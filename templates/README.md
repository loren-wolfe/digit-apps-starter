# Templates

Integration apps you can copy and point at your own accounts. Each one is a full Sutton app
(React + MUI frontend, Cloudflare Worker backend) that started as a customer build and was
generalized: there are no customer names, store URLs, or org-specific ids in the code.
Every account, key, and token is a secret or env var the operator sets in Sutton
(Studio → Settings → Secrets / Environment variables). Secret values never live in this repo.

Start a new app from any of them, from the repo root:

```bash
npm install
npm run new-app -- my-app --from <template-name>
npm run pack -w apps/my-app
```

`new-app` copies the template into `apps/my-app`, renames the package, and writes a fresh
`SPEC.md` stub. Each template's own `README.md` and `SPEC.md` describe setup and behavior in
full; read them before changing the copy.

## [`shipstation-template`](shipstation-template)

Pushes eligible Sutton shipments to one ShipStation account, buys labels, and pulls tracking
back on a 5-minute poll. Supports ShipStation V2 (key only) or V1 (key + secret). Has its own
agent skill in [`.agents/skills/extend-shipstation-app`](shipstation-template/.agents/skills/extend-shipstation-app/SKILL.md)
and a local sandbox viewer described in its README.

| Name | Kind | Purpose |
| --- | --- | --- |
| `SHIPSTATION_API_KEY` | Secret | ShipStation API key. Alone, it connects V2 |
| `SHIPSTATION_API_SECRET` | Secret | Optional. With the key, connects V1 instead |
| `JWT_TOKEN` | Secret | Writes back to Sutton. Generated by Sutton staff |

## [`woocommerce-fulfillment-template`](woocommerce-fulfillment-template)

Lists open Sutton sales orders that came from WooCommerce, polls WooCommerce for completed
orders, then deducts inventory from one default location and marks the Sutton order fulfilled.
Supports virtual kits when the org has a `Kit Type` item field. Nothing is written back to
WooCommerce.

| Name | Kind | Purpose |
| --- | --- | --- |
| `API_TOKEN_SUTTON` | Secret | Sutton organization API token |
| `WC_CONSUMER_KEY` | Secret | WooCommerce REST API key (Read) |
| `WC_CONSUMER_SECRET` | Secret | WooCommerce REST API secret |
| `WC_STORE_URL` | Env var | Store origin, such as `https://shop.example.com` |
| `FULFILLMENT_LOG_SINCE` | Env var | Optional ISO date where polling and the log start |

## [`shopify-item-publish-template`](shopify-item-publish-template)

Publishes one Sutton item (and optionally its sibling sizes) as a product in one or both of
two Shopify stores, such as retail and B2B. New products are drafts; later pushes update the
matching product by SKU. Shopify product and variant ids are written back to the Sutton items.
The field mapping assumes item custom fields like Style#, Color, and Size; adjust
`src/backend/mapping.js` for your own catalog.

| Name | Kind | Purpose |
| --- | --- | --- |
| `API_TOKEN_SUTTON` | Secret | Sutton API token with Read items, Read item cost info, Update items |
| `SHOPIFY_STORE_A_SHOP` / `_B_SHOP` | Secret | Store subdomain, such as `my-retail-store` |
| `SHOPIFY_STORE_A_CLIENT_ID` / `_B_CLIENT_ID` | Secret | Client ID from the store's Dev Dashboard app |
| `SHOPIFY_STORE_A_CLIENT_SECRET` / `_B_CLIENT_SECRET` | Secret | Client secret from the same app |

## Adding a template

Templates in this folder are public. Before adding one:

1. Remove customer names, store domains, emails, and hardcoded Sutton ids (custom field,
   option, location, or adjustment reason ids). Resolve ids by name at runtime or read them
   from an env var.
2. Keep secrets in Sutton. Commit only `*.example` env files with placeholder values.
3. Leave out build outputs (`frontend/`, `backend/`, `app.zip`), `node_modules/`, logs, and
   local data such as `tmp/`.
4. Confirm `npm run pack -w templates/<name>` succeeds, then add a section above.
